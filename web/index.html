AgentCore Runtime 웜풀 데모

콜드스타트를 세션 재사용으로 제거하는 두 방식을 실제로 호출해 비교합니다. 표시되는 지연은 매 호출의 실측값입니다.
콜드 p50 1,328ms 웜 p50 101ms 차이 13배 AWS 관리형 풀 10개 idle 최소 60초

세션 관리 방식 선택에 따라 요청 바디가 달라집니다

방식 2 · 저장소 TTL 추천
서버가 세션을 기억합니다. 만료 판단을 TTL 780초가 대신하므로 시간 비교 코드가 없습니다.
요청 → {userId, prompt} · 클라이언트는 uuid를 모릅니다
방식 1 · 클라이언트 타이머
브라우저가 uuid와 마지막 호출 시각을 보관하고 13분 경과를 직접 계산합니다. 추가 인프라가 없는 대신 uuid 위조가 가능합니다.
요청 → {userId, prompt, sessionId, lastCallAt}

대화 응답 배지에서 콜드/웜을 확인하세요

시나리오 원클릭 재현

① 연속 질문 3회
같은 세션을 재사용합니다. 첫 질문만 pool, 이후는 reused가 되고 전부 웜이어야 합니다.
② 세션 종료 후 재질문
microVM을 강제 종료해 15분 만료를 시뮬레이션합니다. 풀에 재고가 있으면 pool로 다시 웜, 없으면 fresh로 콜드가 됩니다.
③ 풀 소진시키기
신규 유저를 연달아 만들어 재고를 다 씁니다. 재고가 있는 동안 pool(웜), 바닥나면 fresh(콜드)로 지연이 급등합니다. 웜풀이 왜 필요한지 보여주는 핵심 시나리오입니다.
④ 두 방식 A/B 비교
같은 질문을 두 방식으로 각각 던져 지연을 나란히 봅니다. 결과는 비슷해야 정상입니다 — 두 방식의 차이는 지연이 아니라 운영 특성(클라이언트 수정 여부·위조 가능성)에 있습니다.

웜풀 재고 3초마다 갱신

-
큐에 uuid가 있다는 것이 살아있다는 보장은 아닙니다. 15분간 호출이 없으면 microVM만 죽고 uuid 껍데기가 남습니다. heartbeat가 그것을 막습니다.
