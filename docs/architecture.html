1왜 필요한가 — 실측 근거

동일 코드를 두 배포 방식으로 서울 리전에 배포해 측정한 결과입니다. 세션 재사용의 이득이 배포 방식 선택보다 훨씬 큽니다.

구분p50비고
콜드스타트 (직접 코드)1,328ms새 microVM 프로비저닝
웜스타트 (세션 재사용)101ms13배 빠름
콜드스타트 (컨테이너, 예열 히트)379msAWS 관리형 풀 — 10개 한정
콜드스타트 (컨테이너, 풀 소진)3,337ms직접 코드보다 2.4배 느림
AWS 관리형 웜풀은 10개입니다 (실측) 버스트 30개·60개 테스트에서 모두 정확히 10건만 예열 히트했습니다. 크기 지정·조회 API가 없고(CreateAgentRuntime 파라미터에 없음), Service Quotas에도 항목이 없습니다. 필요량(수백 개)에 미달하므로 자체 풀을 만드는 것입니다.
목표 게임 중 지속적이면서 간헐적으로 질문받는 챗봇. 유저가 콜드스타트를 못 견뎌 idle을 15분으로 잡았고, 그 상태에서 모든 요청을 101ms로 처리하는 것이 목표입니다.

왜 idle 축소나 idle=0이 답이 아닌가

안결과판정
idle = 0 REJECTED: valid min value: 60 — 실측 불가
idle = 60초 질문 주기가 60초보다 길면 매 질문이 새 세션 → 세션 생성률 183 TPS 쿼터 초과
idle = 15분 (현행) 동시 세션 71,500 — 그중 약 77%가 유저가 떠난 유휴 꼬리 웜풀 필요

2공통 컴포넌트

두 방식이 공유하는 부분입니다. 차이는 세션 ID를 누가 어떻게 기억하는가뿐입니다.

import langgraph, redis          # ← warmup 이 이걸 데워줘야 의미가 있음

def handler(payload):

        return {"status": "warm"}   # LLM·툴·과금 compute 만 건너뜀

함정 — lazy import 를 과하게 쓰면 예열이 무의미해집니다 무거운 import를 핸들러 안으로 옮기면 warmup은 통과하는데 첫 질문에서 초기화가 터져 콜드스타트가 그대로 발생합니다. 조기 반환은 LLM 호출과 툴 실행만 건너뛰어야 하고, import·클라이언트 생성은 모듈 스코프에서 이미 끝나 있어야 합니다.

단 Redis 클라이언트는 모듈 스코프 유지가 맞습니다. 핸들러 내부에서 생성하면 요청마다 커넥션이 늘어납니다.

이 분리가 웜풀 성립의 전제입니다 둘을 같게 쓰면 세션 ID가 이미 유저 것으로 정해져 풀에서 꺼내 쓸 수 없습니다. 분리하면 uuid가 매번 바뀌어도 ListEvents(sessionId="chat-{userId}")로 이력이 복원됩니다.

확인할 코드 한 줄: memory.create_event(sessionId=f"chat-{user_id}", actorId=user_id, ...) — 여기에 runtime_session_id가 들어가 있으면 안 됩니다.

3방식 1 — 클라이언트 타이머

클라이언트가 uuid와 마지막 호출 시각을 보관하고, 13분 경과를 직접 계산합니다.

장점
  • 추가 인프라 0 — Redis·DynamoDB 불필요
  • 조회 지연 0 (로컬 메모리)
  • 외부 저장소 장애와 무관
단점
  • 게임 클라이언트 수정 필요 — 배포 주기에 묶임
  • 시간 비교 로직이 클라이언트에 상주
  • uuid 위조 가능 — 남의 세션에 붙을 수 있음
  • 멀티 디바이스 시 기기별 세션 → 세션 수 증가
보안 — uuid 위조 클라이언트가 uuid를 들고 있으면 다른 유저의 uuid를 보내 그 세션에 붙을 수 있습니다. runtimeUserId는 검증되지 않습니다(실측). 막으려면 프록시에서 uuid↔userId 매핑을 검증해야 하고, 그러려면 서버 저장소가 다시 필요해져 방식 1의 이점이 사라집니다.
타이머 스레드는 필요 없습니다 백그라운드 타이머가 아니라 요청 보낼 때 시각 비교 1회입니다. 리소스 부담 없습니다.

4방식 2 — Redis TTL 추천

Redis에 TTL 780초로 uuid를 저장합니다. 만료 판단을 Redis가 대신하므로 시간 비교 코드가 사라지고, 클라이언트는 uuid를 아예 모릅니다.

프록시 로직 — 이게 전부입니다

def resolve_session(user_id):
    k = f"sess:{user_id}"
    try:
        uuid = _redis.get(k)
    except RedisError:
        return None   # ⚠️ 여기서 pop 하면 장애 시 풀이 순식간에 고갈된다
    if not uuid:
        uuid = pop_from_queue()          # TTL 만료 또는 최초
        _redis.setex(k, 780, uuid)
    else:
        _redis.expire(k, 780)            # 슬라이딩 — 쓸 때마다 갱신
    return uuid
장점
  • 게임 클라이언트 수정 불필요 ⭐
  • 시간 비교 코드 없음 — TTL이 판단
  • uuid 위조 불가 (서버만 앎)
  • 서버만 고쳐서 배포 가능
  • 세션 스토어를 이미 쓰고 있다면 필드 하나 추가
단점 / 리스크
  • 조회 지연 ~1ms 추가
  • Redis 장애가 세션 라우팅에 전파 ⚠️
  • 현재 겪고 있는 커넥션 이슈가 이 경로에 들어옴
  • 멀티 디바이스 시 세션 공유 (의도한 동작일 수 있음)
폴백 정책이 핵심입니다 Redis 조회 실패 시 큐에서 pop하면 안 됩니다. 장애가 나면 전 유저가 MISS 처리되어 풀이 순식간에 고갈되고 전면 콜드스타트가 됩니다. fail-open 구조라면 조용히 그렇게 됩니다.

Redis 장애 시엔 기존 uuid 재사용 또는 그냥 새 uuid 생성(콜드스타트 감수)이 맞습니다. 일부가 1,328ms를 먹는 게 전체가 먹는 것보다 낫습니다.
대안 — DynamoDB TTL Redis 커넥션 문제(좀비 커넥션 / 복제 지연 / 풀 고갈)가 해결되지 않은 상태라면 DynamoDB가 안전합니다. 세션 라우팅이 Redis 장애와 분리됩니다.
단 DDB TTL은 삭제가 최대 48시간까지 지연되므로 ttl 값을 직접 비교해야 합니다 → 시간 비교 코드가 부활합니다.

5Heartbeat — 재고 유지

큐에 있는 세션도 15분 후 죽습니다. AgentCore는 그 세션이 웜풀용인지 모르고, 호출이 없으면 idle timeout을 적용합니다. 

   SQS:  [uuid-1] [uuid-2] [uuid-3] [uuid-4]
          살아있음   살아있음   죽음     죽음      ← 큐만 보면 구분 불가

   죽은 uuid 를 pop 해서 쓰면 ──▶ 콜드스타트 1,328ms  (에러는 아님, HTTP 200)

두 가지 대응

방법동작비용
Heartbeat
원문 권고		 12~13분마다 재고 전체에 {"type":"warmup"} 핑 → idle 타이머 리셋 재고 214개 기준 0.3 TPS
데이터플레인 1,000 TPS 대비 무시 가능
TTL 폐기 큐 메시지에 적재 시각 기록 → 13분 지난 건 버리고 새로 채움 재생성 0.27 TPS
세션 생성률 61 TPS 대비 미미
실제로는 거의 발동하지 않습니다 재고 소비 61/s면 214개가 약 3.5초에 한 바퀴 회전합니다. 피크 시간엔 만료될 틈이 없습니다.

문제는 저트래픽 시간대(새벽)입니다. 재고가 그대로 앉아 있다가 전부 죽고, 아침 첫 유저들이 콜드스타트를 맞습니다. → heartbeat는 이 구간용 안전망입니다. 그 시간대엔 재고를 줄여도 되므로(원문도 오프피크 축소 권고) heartbeat 부담도 함께 내려갑니다.
원문에서의 위치 — 참고 원문(Minimizing startup latency with Amazon Bedrock AgentCore Runtime)의 아키텍처 4개 구성요소에 heartbeat는 없습니다. "프로덕션 구현에 일반적으로 추가된다"는 목록에 이름만 한 줄 올라가 있고, 주기·구현은 제시되지 않습니다. 12~13분은 idle 15분에서 역산한 값입니다.

또한 "팔려나간 세션이 15분 후 죽는 케이스"는 원문에 아예 없습니다 — 원문 전제가 "유저 상호작용에 의존하지 않는 워크로드"이기 때문입니다. §6의 시나리오 2·3은 이 문서에서 설계한 부분입니다.

heartbeat 로 살려도 8시간이면 강제 종료
  ──▶ 적재 시각 기준 7시간대에 선제 교체 필요

6시나리오별 동작

방식 2(Redis TTL) 기준입니다. 모든 정상 시나리오에서 콜드스타트가 0입니다.

  1. 대화 첫 시작
    Redis MISS → SQS pop → setex(780) → 인보크 101ms
  2. 15분 내 연속 질문
    Redis HIT → 같은 uuid → warm microVM 재사용 → expire 갱신 101ms · 큐 소비 0
  3. 창 열어둔 채 15분 후 질문 원문에 없는 케이스
    microVM은 죽었지만 창 상태와 무관 → Redis TTL도 만료 → MISS → SQS pop 101ms
  4. 창 닫고 재방문
    닫을 때 redis.del + StopRuntimeSession → MISS → SQS pop 101ms
  5. 창 닫기
    StopRuntimeSession(약 8초, fire-and-forget) → 유휴 15분 꼬리 반납
  6. 큐가 비었을 때 degradation
    새 uuid 그냥 생성 → 그 자리에서 부팅 1,328ms — 에러는 아님(HTTP 200)
  7. 죽은 uuid를 pop한 경우
    heartbeat 누락분 → 새 microVM 자동 생성 1,328ms — 에러는 아님
  8. Redis 장애
    폴백: 기존 uuid 또는 새 uuid 1,328ms
    절대 pop하지 말 것 — 풀 고갈로 전면 콜드스타트
시나리오 1·3·4가 같은 코드 한 줄로 처리됩니다 uuid = redis.get(k) or pop_and_store(k)
"만료됐는지"를 조회할 API가 없지만(런타임 세션 상태 조회 API 부재), TTL이 대신 판단하므로 알 필요가 없습니다.

죽은 uuid로 호출하면? — 실측

1) 최초 호출        HTTP 200  1373ms  served=1   ← microVM 생성
2) 같은 uuid 재호출  HTTP 200   139ms  served=2   ← 재사용
   StopRuntimeSession 실행 (= 15분 만료와 동일 상태)
3) 죽은 uuid 로 호출 HTTP 200  1453ms  served=1   ← 새 microVM, 같은 uuid

uuid는 내가 정한 문자열이라 소멸하지 않습니다. microVM만 죽고 이름표는 남아, 다시 부르면 새 microVM이 붙습니다. 에러가 없으니 실패 처리 로직은 불필요하지만, 콜드스타트는 그대로 발생합니다. 그래서 큐에서 새로 꺼내는 것입니다.

부수 효과 — 동시 세션 4.3배 감소

현재:  61/s × 19.5분 (사용 4.5분 + 유휴 15분) = 71,500 세션
       └─ 약 77% 가 유저가 이미 떠난 빈 세션

StopRuntimeSession 적용:
       61/s × 4.5분                            = 16,500 세션
단, 닫기 이벤트는 안 오는 경우가 많습니다 X 버튼은 잡히지만 앱 강제 종료·크래시·네트워크 끊김·게임 클라이언트 종료는 안 옵니다. 게임 클라이언트 내부라 beforeunload류도 신뢰할 수 없습니다. 실제 절감률 = 닫기 이벤트 포착률이고, 못 받으면 기존처럼 15분 후 자동 종료되므로 손해는 없습니다.

이것이 EC2 800대 확보 압박을 줄이는 가장 큰 레버입니다 — 웜풀과 별개로 즉시 유효합니다.

7풀 크기 산정

원문 공식: 필요 풀 = 초당 요청 × 보충 시간

원문 예시:  초당 10 요청 × 보충 3초  = 40개면 콜드스타트 완전 제거

이 워크로드:
   동시 세션 71,500 ÷ 세션 수명 19.5분 = 61 TPS  (세션 생성률)
   보충 시간 ≈ 3.5초  ← 실측 즉석 부팅 시간을 대용값으로 사용

   필요 풀 = 61 × 3.5 ≈ 214개

#항목영향
1보충 속도 (초당 몇 개 채워지나) 214개 계산의 3.5초는 부팅 시간 대용값. 실제 보충률이 낮으면 풀이 더 커야 함
2재방문 빈도 시나리오 3·4의 큐 소비량 → 풀 크기 직접 결정
3챗봇 UI 오픈 → 첫 질문 간격 핑 방식(큐 없이)만으로 충분한지 판단 근거
4닫기 이벤트 포착률 동시 세션 절감 실효치
561 TPS 지속 부하에서의 거동 실측은 버스트 1회뿐 — 원문 측정 원칙 5번 미충족
6고객 콜드스타트 7~10초의 원인 AWS 엔지니어 조사 중. 1.2KB zip이 1,328ms이므로 초기화 코드 문제로 추정

더 단순한 대안 — 핑 방식

큐·heartbeat 없이 되는 방법도 있습니다 원문 완화 사다리의 1순위는 큐가 아니라 "전략적 핑"입니다(큐는 3순위).

유저가 챗봇 UI를 열 때 그 유저의 uuid로 warmup 핑을 쏘고, 타이핑하는 동안 프로비저닝이 끝나게 하는 방식입니다. 재방문도 "다시 여는" 것이므로 같은 방법으로 커버됩니다. SQS·Lambda·heartbeat·풀 크기 산정이 전부 불필요합니다.

성립 조건: UI 오픈 → 첫 질문 간격이 콜드스타트(1,328ms)보다 길어야 합니다. 보통 타이핑에 수 초가 걸리므로 충분할 가능성이 높습니다 → 미확인 #3.

⚠️ 예열 시점은 반드시 챗봇 UI 오픈이어야 합니다. 게임 로그인 시점에 하면 챗봇을 쓰지 않는 유저 몫까지 세션을 만들어 사용률 20% 가정 시 5배를 낭비합니다.

실행 우선순위

  1. 콜드스타트를 클라이언트에서 계측
    CloudWatch에 콜드스타트 전용 메트릭이 없습니다. Latency는 LLM 시간까지 포함한 end-to-end라 분리 불가 → 개선 효과를 증명할 수단부터 확보
  2. 초기화 코드 점검
    의존성 번들 여부, 모듈 스코프 무거운 import → 7~10초의 실제 원인일 가능성이 높음
  3. Memory sessionId 분리 확인
    create_event(sessionId=...)에 runtime_session_id가 들어가 있으면 웜풀 자체가 성립하지 않음
  4. StopRuntimeSession 적용
    웜풀과 무관하게 즉시 유효. 동시 세션·EC2 압박 완화
  5. 쿼터 증설 — L-8EE2AEA2 + L-3E5722B2 세트
  6. 핑 방식 먼저 시도 → 부족하면 SQS 웜풀

9실배포 검증 결과 2026-09-14

이 문서의 설계를 실제로 AWS에 배포해 두 방식 모두 동작을 확인했습니다. 아래는 실행 로그에서 그대로 옮긴 값입니다. 데모 코드는 github.com/blait/AgentCoreWarmPool 에 있습니다.

⚠️ 아래 로그와 현재 커밋의 차이 — 이 로그를 얻은 뒤 코드 리뷰에서 배포 결함 세 가지를 찾아 고쳤습니다. 로그를 만든 실행본과 현재 트리는 아래만큼 다릅니다.
  1. RUNTIME_REGION — 프록시가 모듈 스코프에서 필수로 읽는데 deploy.sh가 주입하지 않았습니다. 지금은 주입 + AWS_REGION 폴백 양쪽을 갖췄습니다. 아래 지연·source 값은 세션 선택 로직의 결과이고, 그 로직은 이 수정으로 바뀌지 않았습니다.
  2. heartbeat 스케줄러 — 로그를 얻을 때 heartbeat는 손으로 호출했습니다. EventBridge 규칙은 이 수정에서 새로 추가했고 아직 실측하지 않았습니다.
  3. 큐 보관 기간 — 1시간이었습니다. 즉 §7의 8시간 rolling replacement는 당시 도달 불가능한 코드였고, 지금도 실측되지 않았습니다(보관 기간만 8시간으로 올려 도달 가능하게 만든 상태입니다).
요약하면 1회성 지연 측정치는 유효하고, 시간이 지나야 드러나는 항목(heartbeat 자동 주기, 8시간 교체)은 미검증입니다.

방식 2 (저장소 TTL) — 연속 질문

질문1:  117.9ms  source=pool     cold=False  uptime=8149ms  turn=1  restored=True
질문2:  104.5ms  source=reused   cold=False  uptime=8392ms  turn=2  restored=False
질문3:   84.2ms  source=reused   cold=False  uptime=8604ms  turn=3  restored=False

uptime 8,149ms — 요청이 도달하기 8초 전에 이미 부팅되어 있던 microVM에 안착했습니다. 첫 질문이 pool, 이후가 reused로 전환되는 것도 설계대로입니다.

방식 1 (클라이언트 타이머) — 13분 경과 감지

q1:  107.2ms  source=pool     uptime=23995ms
q2:   95.0ms  source=reused   uptime=24406ms
lastCallAt 을 900초 과거로 설정 (13분 초과 시뮬레이션)
→   125.0ms  source=pool     uptime=27346ms   ← 만료를 감지해 큐에서 새로 꺼냄

⭐ 풀 소진 — 웜풀이 필요한 이유

재고 2개 상태에서 신규 유저 6명 연속 요청

유저1:   100.4ms  source=pool     웜
유저2:   134.2ms  source=pool     웜
유저3:  1307.7ms  source=fresh    콜드  ← 재고 바닥
유저4:  1296.7ms  source=fresh    콜드
유저5:  1349.7ms  source=fresh    콜드
유저6:  1263.2ms  source=fresh    콜드
재고가 있는 동안 100~134ms, 바닥나면 1,263~1,350ms 후자는 §1의 콜드스타트 실측값 1,328ms와 일치합니다. 같은 코드·같은 런타임에서 풀 재고 유무만으로 10배 이상 차이가 난다는 것을 한 번의 실행으로 보여줍니다.

⚠️ 실배포에서 발견한 버그 — heartbeat가 재고를 잠갔다

§5에서 heartbeat를 "부담이 작은 안전망"으로 설명했는데, 구현에는 함정이 있었습니다. 

heartbeat 실행 → {"pinged": 3, "depth": 3}     ← 성공한 것처럼 보인다
SQS 상태        → visible=0, invisible=3        ← 그런데 재고 전부가 잠김
이어진 요청      → 1329.5ms  source=fresh       ← 전 유저가 콜드스타트

가시성 회복까지 약 40초 소요

원인: heartbeat가 재고를 다 훑으려고 receive를 여러 라운드 돌렸는데, 환원한 메시지가 같은 실행에서 다시 잡히며 VisibilityTimeout이 재적용됐습니다. 예열된 세션이 살아 있는데도 pop이 빈손이 되어, 웜풀의 목적 자체가 무너지는 버그입니다.

수정: receive를 1회(최대 10건)로 제한. 처리한 메시지는 전부 delete되므로 재고가 잠기지 않습니다. 재고가 10개를 넘으면 함수를 여러 번 호출합니다. 

수정 후:
heartbeat → {"pinged": 7, "depth": 7}   ·  SQS: visible=7, invisible=0
직후 요청1:  95.5ms  source=pool  웜
직후 요청2: 103.7ms  source=pool  웜
이 버그가 시사하는 것 원문에 heartbeat는 "필요하다"는 한 줄로만 있고 구현이 없습니다(§5 참조). 실제로 구현해보면 SQS 가시성 관리가 웜풀 운영의 핵심 난점이고, 잘못하면 풀을 운영하는데도 전 유저가 콜드스타트를 맞습니다. 운영 전에 "heartbeat 직후 pop이 웜인가"를 반드시 검증해야 합니다.
