# 아키텍처 — 두 가지 웜풀 방식

이 문서는 [README](../README.md)의 두 방식을 요청 단위로 분해합니다.

**수치 규칙**: 실측값은 콜드 **1,328ms** / 웜 **101ms** 두 개뿐입니다. 이 문서의 나머지 지연값은
모두 이 두 값에서 유도한 **추정치**이며 "추정"으로 표시합니다.

---

## 1. 문제 — 왜 세션 ID가 지연을 결정하는가

AgentCore Runtime은 **세션 1개당 microVM 1개**를 띄웁니다. 요청이 오면 둘 중 하나입니다.

```
[콜드]  이 세션의 microVM이 없다
          ① microVM 프로비저닝
          ② 배포 아티팩트 로딩
          ③ 런타임 초기화
          ④ 내 시작 코드 실행 (import, 클라이언트 생성)
        → 네 단계 전부가 유저 대기시간.  실측 1,328ms

[웜]    같은 세션 ID로 재호출 → 기존 microVM 재사용 → ①~④ 전부 건너뜀
        → 실측 101ms
```

따라서 웜풀의 정체는 **"쓸 수 있는 세션 ID를 미리 만들어두는 것"** 입니다. microVM을 직접
제어하는 수단은 없습니다(웜풀 크기 조회·지정 API가 없음 — README §6-6).

### 세션 라이프사이클

| 상태 | 설명 |
|---|---|
| **Active** | 핸들러 실행 중 |
| **Idle** | 실행 완료. microVM은 프로비저닝된 채 유지. **메모리 과금 계속** |
| **Terminated** | idle 타이머 만료 / 최대 수명 도달 / 명시적 종료 |

- `idleRuntimeSessionTimeout` 기본 **15분**, 범위 **60초 ~ 8시간**. `idle=0`은 API가 거부합니다
  (`valid min value: 60`).
- **최대 세션 수명 8시간, 초과 불가.**

> **핵심 함정**: 만료된 세션 ID로 호출해도 **에러가 아닙니다.** HTTP 200 + 콜드스타트로 응답합니다(실측).
> 세션 만료는 예외로 드러나지 않고 **지연으로만** 드러나므로, 로그에 에러가 없다고 정상인 것이 아닙니다.

## 2. 세션 ID 두 종류의 분리 — 모든 설계의 전제

```
runtimeSessionId  = uuid4()          33자 이상 필수. microVM 식별. 교체 가능
memorySessionId   = "chat-{userId}"  유저 고정. 대화 이력. uuid와 완전히 독립
```

두 값을 하나로 쓰면 웜풀 자체가 성립하지 않습니다. 미리 만들어둔 uuid는 유저를 모르는 상태에서
생성되므로, 이력이 uuid에 묶여 있으면 그 uuid를 누구에게도 줄 수 없습니다.

```
[분리 안 됨]  uuid = 대화 = 유저     → 미리 만든 uuid는 "빈 대화"이자 "주인 없는 세션"
                                       → 풀에서 꺼내 쓸 수 없다

[분리 됨]     uuid  = microVM (교체 가능, 재고화 가능)
              msid  = 대화 (유저에 고정, microVM이 죽어도 살아남음)
                                       → uuid를 자유롭게 갈아끼울 수 있다
```

에이전트는 `contextRestored`로 이 분리가 작동했음을 보고합니다. microVM이 교체되면 그 VM에
이력 캐시가 없으므로 `contextRestored: true`가 되고, 실제 구현에서는 이 지점에서 AgentCore
Memory의 `ListEvents`를 호출합니다.

## 3. 방식 1 · client — 클라이언트가 만료를 계산

클라이언트가 `uuid`와 `lastCallAt`을 보관하고, 13분이 지났는지 스스로 판단합니다.
(idle 기본값 15분에 대해 **13분은 안전 마진**입니다. 왕복 지연과 기기 시계 오차를 흡수합니다.)

### 요청 흐름

```
① 브라우저   localStorage에서 sessionId, lastCallAt 로드
② 브라우저   now - lastCallAt < 13분 ?
                YES → sessionId 그대로 전송
                NO  → sessionId 없이 전송 (버림)
③ POST /api/chat { mode:"client", userId, prompt, sessionId?, lastCallAt? }
④ Lambda     sessionId 있으면 그대로 사용        → source="reused"
             없으면 SQS FIFO에서 pop            → source="pool"
             큐가 비었으면 uuid4() 즉석 생성      → source="fresh"
⑤ Lambda     InvokeAgentRuntime(runtimeSessionId=위 값,
                                payload={prompt, userId, memorySessionId:"chat-"+userId})
⑥ Lambda     응답의 uptimeMs로 coldStart 판정 (> 1500 이면 웜)
⑦ Lambda     source="pool" 이었으면 보충을 비동기 트리거 (응답을 블로킹하지 않음)
⑧ 브라우저   응답의 sessionId를 저장하고 lastCallAt = now
```

**약점이 ②에 집중됩니다.** 판단이 클라이언트 기기 시계에 의존하고, 클라이언트가 uuid를 알기
때문에 위조할 수 있고, 로직을 바꾸려면 클라이언트를 재배포해야 합니다.

## 4. 방식 2 · store — DynamoDB TTL이 만료를 판단 ★추천

클라이언트는 `userId`만 보냅니다. 만료 판단은 **DynamoDB TTL이 항목을 지우는 것**으로 대체됩니다.
서버에도 시간 비교 코드가 없습니다 — "항목이 있으면 살아있고, 없으면 죽었다"입니다.

### 요청 흐름

```
① POST /api/chat { mode:"store", userId, prompt }
② Lambda     GetItem(TABLE_NAME, pk=userId)
                항목 있음 → 그 sessionId 사용                → source="reused"
                항목 없음 → SQS FIFO에서 pop                 → source="pool"
                큐도 비었음 → uuid4() 즉석 생성               → source="fresh"
③ Lambda     InvokeAgentRuntime(runtimeSessionId, payload)
④ Lambda     PutItem(pk=userId, sessionId, ttl=now+13분)     ← 매 호출마다 TTL 갱신
⑤ Lambda     uptimeMs로 coldStart 판정 → 응답
⑥ Lambda     source="pool" 이었으면 보충을 비동기 트리거
```

### TTL을 만료 판단에 쓸 때의 주의

**DynamoDB TTL 삭제는 즉시가 아닙니다.** 만료 시각이 지나도 항목이 실제로 지워지기까지
지연이 있을 수 있습니다. 따라서 **TTL만 믿으면 이미 죽은 세션 ID를 꺼내 쓸 수 있습니다.**

이 데모는 TTL을 **재고 정리 수단**으로 쓰고, 판정은 항목에 함께 저장한 만료 시각을 서버가
읽어 확인하는 방식으로 처리합니다. TTL 13분이 idle 15분보다 짧게 잡혀 있으므로, 삭제가
늦어져도 만료 시각 비교에서 걸러집니다.

> 판정을 클라이언트에서 서버로 옮긴 것이 이 방식의 이득이지, "시간 비교가 세상에서
> 사라진다"는 뜻은 아닙니다. 다만 그 코드가 **한 곳(서버)에만** 있게 됩니다.

## 5. 8개 시나리오 — 예상 지연과 `source`

지연은 `1,328ms`(콜드) / `101ms`(웜) 두 실측값에서 유도한 **추정치**입니다. Lambda·DynamoDB·SQS
왕복은 포함하지 않았습니다.

| # | 시나리오 | `source` | `coldStart` | 예상 지연 (추정) | 유저가 느끼는 것 |
|---|---|---|---|---|---|
| **1** | **첫 시작** — 방문 직후 첫 질문 | `pool` | `false` | **~101ms** | 빠름 ✅ |
| **2** | **15분 내 연속 질문** | `reused` | `false` | **~101ms** | 빠름 ✅ |
| **3** | **창 열어둔 채 15분 후** 질문 | `pool` | `false` | **~101ms** | 빠름 ✅ |
| **4** | **창 닫고 재방문** | `pool` | `false` | **~101ms** | 빠름 ✅ |
| **5** | **창 닫기** (세션 종료) | — | — | — | 없음 (백그라운드) |
| **6** | **큐가 비었을 때** | `fresh` | `true` | **~1,328ms** | 느림 ⚠️ |
| **7** | **죽은 uuid를 pop** | `pool` | `true` | **~1,328ms** | 느림 ⚠️ |
| **8** | **store 장애** (DynamoDB) | `pool` 또는 `fresh` | 상황에 따라 | ~101ms ~ ~1,328ms | 상황에 따라 |

### 각 시나리오의 내부 동작

**① 첫 시작**
클라이언트에 세션이 없고 DynamoDB에도 항목이 없습니다. 큐에서 예열 uuid를 pop합니다.
그 uuid의 microVM은 `warmup` 핑으로 이미 부팅·초기화를 마쳤으므로 ①~④를 건너뜁니다.
**콜드스타트를 유저 대기 밖으로 밀어낸 지점이 정확히 여기입니다.** 응답 후 보충이 비동기로 돕니다.

**② 15분 내 연속 질문**
같은 uuid를 재사용합니다. 두 방식 모두 `reused`. 이때 `contextRestored: false`이고 `turn`이
증가합니다 — 같은 microVM이 이력을 들고 있다는 증거입니다.

**③ 창 열어둔 채 15분 후**
microVM은 idle 타이머로 이미 죽었습니다. 방식 1은 클라이언트가 13분 경과를 계산해 uuid를
버리고, 방식 2는 TTL로 항목이 사라져 있습니다. **양쪽 모두 새로 pop하므로 유저는 여전히 빠릅니다.**
`contextRestored: true`가 되어 이력 복원이 일어났음이 드러납니다.

> 만약 만료 계산이 없다면 이 시나리오가 곧 **시나리오 7**(죽은 uuid pop)이 되어 1,328ms를 맞습니다.
> 13분 마진의 존재 이유입니다.

**④ 창 닫고 재방문**
방식 1은 `localStorage`가 남아 있으면 오래된 uuid를 들고 오지만 13분 계산에서 걸러집니다.
방식 2는 클라이언트 상태를 전혀 신뢰하지 않으므로 `userId`만으로 판단합니다 —
**기기를 바꿔 접속해도 동작이 같습니다.** 방식 1은 이 경우 항상 새 uuid를 받게 됩니다.

**⑤ 창 닫기**
`POST /api/session/end`로 세션을 명시적으로 종료합니다. **비용 관점에서 중요합니다** — 종료하지
않으면 idle 15분 동안 메모리 과금이 계속됩니다. 다만 브라우저 종료 시 요청 전송이 보장되지
않으므로(`beforeunload`는 신뢰할 수 없습니다), 이 호출은 **최선 노력이며 idle 타임아웃이
최종 안전망**입니다.

**⑥ 큐가 비었을 때**
버스트로 재고가 소진된 상태입니다. `uuid4()`를 즉석 생성하고 그 자리에서 부팅합니다 —
**웜풀이 없는 것과 동일한 지연**입니다. 실패가 아니라 성능 저하(graceful degradation)로
처리되며, 이 상황이 얼마나 자주 오는지가 풀 크기 적정성의 지표입니다. `/api/pool`의
`depth`가 0에 붙어 있으면 재고가 부족한 것입니다.

**⑦ 죽은 uuid를 pop**
**가장 눈에 띄지 않는 실패입니다.** 큐에 uuid는 남아 있지만 그 microVM은 idle 만료로 이미
죽었습니다. pop은 성공하고 호출도 HTTP 200으로 성공하지만, 실제로는 콜드스타트가 발생해
**"웜풀이 있는데도 느린"** 상태가 됩니다. 에러 로그에 아무것도 남지 않습니다.

→ **heartbeat가 필요한 이유가 이것입니다** (§6). 재고의 나이를 감시해야 하며, `/api/pool`이
`ageSec`와 `staleRisk`를 노출하는 것이 이 목적입니다.

**⑧ store 장애 (DynamoDB)**
방식 2의 유일한 구조적 약점입니다. `GetItem`이 실패하면 세션 매핑을 알 수 없습니다.
**세션 조회 실패를 채팅 실패로 만들지 않는 것**이 원칙입니다.

```
GetItem 실패 → 재사용 가능한 세션을 "모른다"고 처리
             → 큐에서 pop (source="pool", 유저는 빠름)
             → 큐도 비었으면 uuid4() (source="fresh", 느리지만 동작함)
```

즉 **DynamoDB 장애의 영향은 "지연 증가"이며 "채팅 중단"이 아닙니다.** 대신 `PutItem`도
실패하므로 그 동안은 세션 재사용이 되지 않아 매 요청이 재고를 소모합니다 — 장애가 길어지면
재고가 마르고 시나리오 6으로 수렴합니다. 방식 1에는 이 실패 모드가 아예 없습니다(의존 대상이 없음).

## 6. heartbeat — 재고가 썩는 것을 막는다

**문제**: 큐에 넣어둔 uuid는 그 자체로는 아무 일도 하지 않습니다. 마지막 활동(예열 핑)으로부터
idle 타임아웃이 지나면 microVM이 죽고, 큐에는 **껍데기 uuid만 남습니다.**

```
t=0      replenish: uuid 생성 + warmup 핑 → microVM 부팅       [재고 유효]
t=15분   idle 타임아웃 → microVM terminated                    [재고 무효]
t=20분   유저가 pop → HTTP 200 + 콜드스타트 1,328ms            [조용한 실패]
                     └ 에러 없음. 웜풀이 있는데도 느리다
```

**해결**: 재고 세션에 주기적으로 `{"type":"warmup"}` 핑을 보내 idle 타이머를 리셋합니다.
`POST /api/pool/heartbeat`가 이 일을 합니다.

**엔드포인트만으로는 부족하고 그것을 부르는 스케줄러가 있어야 합니다.** 이 데모는
`deploy.sh`가 EventBridge 규칙 `<stack>-heartbeat`를 만들어 Lambda를 직접 호출합니다
(API Gateway를 거치지 않고, `rawPath: "/api/pool/heartbeat"` 모양의 이벤트를 넣습니다).
UI의 `heartbeat 실행` 버튼은 **시연용**입니다 — 사람이 누르는 것에 의존하면 아무도 보지 않는
동안 재고가 썩습니다.

주기는 **idle 타임아웃보다 충분히 짧아야** 합니다. 핑 실패·재시도 시간까지 흡수하도록
`idle / 3`으로 잡습니다(기본 `idle=900초` → **5분**). `HEARTBEAT_MINUTES`로 덮어쓸 수 있습니다.
핑이 한 번 실패한 것과 microVM이 죽은 것을 구분할 수 없으므로,
**재시도 후에도 실패하면 그 uuid는 재고에서 버리는 것**이 안전합니다.

`_heartbeat()`는 1회 호출에 `receive` 1회(최대 10건)만 처리하므로(§ 아래 가시성 문제),
재고가 10개를 넘으면 규칙에 타깃을 여러 개 두어 병렬 호출합니다
(`POOL_TARGET / 10`, 최대 5개).

> **재고를 하드 삭제하는 또 하나의 시한폭탄**: SQS `MessageRetentionPeriod`입니다.
> 이 값이 지나면 SQS가 메시지를 지우므로, heartbeat가 살려둔 세션의 uuid까지 사라집니다
> (세션은 살아 있고 아무도 모르므로 idle 만료까지 메모리 과금만 남습니다).
> 그래서 보관 기간은 microVM 최대 수명(8시간) **이상**이어야 합니다. 그보다 짧으면
> 아래 §7의 rolling replacement 판정에 도달하는 메시지가 아예 없어져 그 분기가 죽습니다.

**heartbeat가 저렴한 이유**는 에이전트의 `warmup` 조기 반환입니다.

```python
# agent/main.py — 이 조기 반환이 없으면 heartbeat 비용 = 실제 대화 비용
if payload.get("type") == "warmup":
    return {"status": "warm"}      # LLM·툴·과금 compute 전부 건너뜀
```

이 분기가 LLM 호출 **앞에** 있어야 합니다. 뒤에 두면 재고 유지가 대화만큼 비싸집니다.

> **단, heartbeat는 비용을 0으로 만들지 않습니다.** 세션을 계속 살려두므로 **메모리 과금이
> 유지되는 시간이 길어집니다.** heartbeat는 "재고를 유효하게 유지하는 비용"과 "재고가 썩어
> 콜드스타트를 맞는 손실"의 교환입니다.

## 7. 8시간 rolling replacement — 교체는 선택이 아니다

**microVM 최대 수명은 8시간이고 이 값을 초과할 수 없습니다.** heartbeat로 idle 타이머를 계속
리셋해도 **8시간이 되면 강제 종료**됩니다.

```
t=0        재고 uuid 생성
t=13분마다  heartbeat → idle 타이머 리셋 (계속 유효)
t=8시간     ⛔ 최대 수명 도달 → 강제 terminated
           → heartbeat로는 막을 수 없다
           → 이후 pop하면 시나리오 7 (죽은 uuid)
```

따라서 재고는 **8시간 안에 반드시 교체**되어야 합니다. 그리고 교체는 **롤링**이어야 합니다.

**한꺼번에 교체하면 안 되는 이유**가 두 가지입니다.

1. **재고 공백** — 전량을 동시에 버리면 그 사이 모든 요청이 `fresh`(콜드스타트)를 맞습니다.
2. **쿼터 충돌** — 재고 N개를 동시에 다시 만들면 세션 생성이 한꺼번에 몰려
   `L-8EE2AEA2`(계정당 25 TPS)를 칩니다. 스로틀되면 재고 회복이 더 늦어지고,
   그 동안 유저 요청도 같은 쿼터를 두고 경쟁합니다.

→ 재고를 **생성 시각이 서로 다르게** 유지하고 오래된 것부터 조금씩 교체합니다. 재고를 한 번에
   전량 채우는 최초 구축 시점에도 생성 시각이 뭉치므로, 첫 교체 주기에서 의도적으로 시각을
   흩는 것이 좋습니다.

**보충 속도 자체가 쿼터에 종속된다**는 점도 같은 이유에서 중요합니다. 원문은 필요 풀 크기를
`초당 요청 × 보충 시간`으로 계산하지만, **이 레포는 보충 시간을 측정하지 않았습니다**
(README §6-1). 흔히 인용되는 3.5초는 보충 시간이 아니라 **컨테이너 즉석 부팅 시간을 대용한
값**이므로, 이 식에서 나오는 풀 크기는 추정입니다.

## 8. 원문에 있는 것 / 이 레포에서 추가한 것

출처를 섞지 않기 위해 명시적으로 구분합니다.
원문: AWS re:Post [Minimizing startup latency with Amazon Bedrock AgentCore Runtime](https://repost.aws/articles/ARCJIn3t7aRC2FxiRTV1SuCA/minimizing-startup-latency-with-amazon-bedrock-agentcore-runtime).

### 원문에 있는 것

| 항목 | 원문의 내용 |
|---|---|
| 세션 재사용이 지연을 결정 | "startup latency ... closely tied to session ID reuse" |
| SQS FIFO 기반 warm pool | 4개 구성요소: SQS FIFO / `getSessionId` Lambda / `replenish` Lambda / agent handler |
| **pop → 보충** 경로 | pop 후 `replenish`를 비동기 invoke. **원문의 흐름은 여기까지입니다** |
| `warmup` 센티널 조기 반환 | LLM·툴·과금 compute 앞에서 short-circuit |
| 필요 풀 = 초당 요청 × 보충 시간 | 예: 10 req/s × 3초 → 40개 |
| 보충 속도가 세션 생성률 쿼터에 종속 | 명시됨 |
| idle 시 메모리만 과금 | 명시됨 |
| 사전 예열 인스턴스는 컨테이너 전용·엔드포인트별 | 명시됨 |
| 다중 엔드포인트로 풀 배수 확보 | 라운드로빈 분산 |
| 프로덕션에 "추가로 필요한 것" **목록** | heartbeat 루프 / ping 재시도 / 풀 소진 시 graceful degradation / 풀 적정화 메트릭 — **필요하다는 언급까지이고 설계는 제시되지 않습니다** |

### 이 레포에서 추가 설계한 것

| # | 추가한 것 | 왜 필요했는가 |
|---|---|---|
| **1** | **"팔려나간 세션이 15분 후 죽는 케이스"** (시나리오 3) | 원문은 **풀 안의** 세션만 다룹니다. 유저에게 건네준 뒤 그 유저가 15분간 조용하면 세션이 죽는데, 원문에는 이 경로가 없습니다. 방식 1·2의 만료 판단이 전부 이 문제를 위한 것입니다. |
| **2** | **heartbeat 주기의 구체값·스케줄러·실패 처리** | 원문은 "heartbeat 루프가 필요하다"고만 씁니다. 주기(`idle/3`), 그것을 부르는 EventBridge 규칙, 재고 10개 초과 시 타깃 팬아웃, 핑 실패 시 재고 폐기는 모두 이 레포의 판단입니다. |
| **3** | **DynamoDB TTL을 만료 판단에 사용** (방식 2) | 원문에 DynamoDB가 등장하지 않습니다. 클라이언트를 고치지 않아도 되게 만들려는 이 데모의 요구에서 나온 설계입니다. TTL 삭제 지연 대응(§4)도 추가입니다. |
| **4** | **죽은 uuid를 pop하는 케이스** (시나리오 7) | 원문에 없습니다. HTTP 200 + 콜드스타트로 조용히 실패한다는 것은 이 레포의 실측입니다. `staleRisk`·`ageSec` 노출이 여기서 나왔습니다. |
| **5** | **8시간 rolling replacement의 필요성과 방식** | 원문은 최대 수명 8시간을 명시하지만, **재고 교체 전략으로 연결하지 않습니다.** §7의 "한꺼번에 교체하면 쿼터를 친다"는 논증도 추가입니다. |
| **6** | **`source` 3분류** (`reused`/`pool`/`fresh`) | 관측 가능성을 위한 이 레포의 계측 설계입니다. 어느 경로로 세션을 얻었는지 구분해야 풀이 실제로 기능하는지 알 수 있습니다. |
| **7** | **`uptimeMs > 1500` 콜드 판정** | 이 레포의 실측(약 390ms 대 약 3,900ms 이봉분포)에서 정한 경계값입니다. |
| **8** | **`memorySessionId` / `runtimeSessionId` 분리 명시** | 원문 코드는 세션 ID를 하나로 다룹니다. 대화형 워크로드에서 풀을 쓰려면 분리가 필수인데(§2) 원문은 이를 강조하지 않습니다. |
| **9** | **2026-08 쿼터 통합의 함의** | 원문(2026-05 게시) 이후의 변경입니다. 다중 엔드포인트가 **버스트 흡수용이며 지속 트래픽에는 무효**라는 결론은 통합 이후에만 성립합니다. |

### 원문 수치와 이 레포 실측의 차이

같은 현상을 다른 조건에서 측정한 값이므로 **섞어 쓰지 않습니다.**

| | 원문 (2026-04 벤치마크) | 이 레포 실측 |
|---|---|---|
| 온디맨드 p50 | 약 2.9초 | **1,328ms** (직접 코드) |
| 예열 p50 | 약 200ms | **101ms** (세션 재사용) |
| 개선 | 약 93% | **13배** |

수치가 다른 이유는 측정 조건이 다르기 때문입니다. 이 레포는 `ap-northeast-2`에서 1.2KB
아티팩트에 표준 라이브러리만 사용했고 LLM 호출을 넣지 않았습니다. **원문의 값과 이 레포의
값을 한 표에 나란히 놓아 비교하지 마십시오.**

## 9. 관측 — 무엇을 보면 풀이 작동하는지 알 수 있나

| 지표 | 어디서 | 무엇을 뜻하나 |
|---|---|---|
| `source` 분포 | `GET /api/metrics` | `fresh` 비율이 곧 **웜풀 실패율**입니다. 0에 가까워야 합니다 |
| `coldStart` 비율 | `GET /api/metrics` | `source="pool"`인데 `coldStart=true`면 **죽은 재고**입니다 (시나리오 7) |
| `depth` | `GET /api/pool` | 0에 붙어 있으면 재고 부족 (시나리오 6) |
| `ageSec` / `staleRisk` | `GET /api/pool` | 8시간에 가까운 재고 = 교체 대상 (§7) |
| `contextRestored` | `/api/chat` 응답 | `true`면 microVM이 교체되어 이력 복원이 일어났음 |
| `CombinedNewSessionCreation` | CloudWatch `Usage` 네임스페이스 | 세션 생성률 쿼터(25 TPS) 여유. `Bedrock-AgentCore`가 아닙니다 |

**가장 중요한 한 줄**: `source="pool"` **AND** `coldStart=true`의 건수를 보십시오. 이것이 0이 아니면
웜풀이 있는데도 작동하지 않는다는 뜻이며, **에러 로그에는 아무것도 남지 않습니다.**
